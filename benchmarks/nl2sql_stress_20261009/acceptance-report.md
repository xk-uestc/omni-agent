# NL2SQL 难度递增压力验收

## 结论

**本轮未通过验收。** 复杂上下文、多轮追问、派生指标和字面值保护表现稳定，但分组查询经常停在澄清，部分指标别名生成了错误时间范围或统计对象；端到端 P95 为 21.73 秒，也不满足及时回答的要求。

## 测试范围

- 时间：2026-10-09 03:43:30 至 04:20:07（Asia/Shanghai）。截止前启动的最后一条请求完成后写入结果。
- 压测端 HTTP 问答并发：**1**；题目按难度递增，单题逐条发送，多轮题保持会话上下文。
- 数据：项目自建演示 SQLite 数据库和 377 条自编用例，不是公开基准或生产数据。
- 覆盖：全量递增轮完成 242 个唯一用例；为保证在时间窗口内测试到难度 4/5，再运行 74 个代表性尾段用例，共 304 个唯一用例 ID、482 次请求。另有 73 个唯一用例未覆盖，结果不代表 377 条全部通过。
- 先前的初始排序试跑和高并发探索数据均未并入验收统计。

## 主要问题

1. **年份过滤和统计范围错误。** “2025 年营销预算”期望值为 11,582,304，实际返回 59,136,000，生成 SQL 未加 2025 年过滤。营销点击、转化、曝光和归因销售也出现同类全量汇总。库存量/库存金额和客户数还出现快照或统计对象不一致，例如客户数期望 33、实际 131。
2. **分组问题大面积只澄清、不回答。** 69/77 条未生成 SQL。常见追问是要求用户确认日期字段格式或从开始日期、结束日期、跨期重叠中选择口径。业务口径确实不明确时，澄清合理；但演示库中可以通过字段样本验证日期格式，反复把格式问题交给用户说明，说明日期元数据和安全筛选逻辑不足。
3. **部分口语映射过度保守。** “配送成本”“买进花了多少”等有目录候选字段的问法仍出现澄清，不能稳定复用已知业务指标。
4. **仍有一个外部调用长尾超时。** “2025 年广告归因销售额”耗时约 40.0 秒后超时。

## 延迟与资源

- 482 次合并延迟：P50 **228 ms**，P95 **21.73 秒**，P99 **33.34 秒**，最大 **40.01 秒**。
- 健康检查 **57/57** 返回 HTTP 200，没有观察到服务掉线。
- HTTP 问答最大并发为 **1**。资源采样 142 次，工作集峰值约 **606 MB**、线程峰值 **106**；两段平均 CPU 分别约 **0.073** 和 **0.098** 个核心，没有 CPU 饱和迹象。
- 记录到 45 次模型规划调用：`gpt-5.6-sol` 22 次（P50 11.66 秒、P95 23.17 秒），`gpt-5.5` 23 次（P50 8.46 秒、P95 15.58 秒）。模型响应等待与端到端长尾相符；单题中应用自己的 API 备用/竞速逻辑可能发起多个上游尝试，所以“问答并发 1”不等于上游请求总数为 1。

## 验收判断

多轮上下文和复杂派生计算已有明确正向证据，但整体准确率 79.67%、难度 2/3 的错误与澄清比例、21.73 秒 P95 都不足以通过验收。下一轮应优先修正指标目录的时间口径/来源人群、基于真实字段样本推断日期格式，并针对 69 条分组澄清做回归；然后再重跑本报告中的失败题和未覆盖的 73 个用例。
