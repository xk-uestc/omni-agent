# Omni-Agent × QiMem × Agentic RL：长期项目主线与协作协议

> **文件定位：长期战略主线（Source of Truth）**  
> 建立时间：2026-10-09  
> 目标仓库：[xk-uestc/omni-agent](https://github.com/xk-uestc/omni-agent)  
> 开发分支：`memory`（GitHub 远程实际分支名，全部小写）；`main` 为比赛稳定主线。

## 0. 一句话定位

建立一套**可验证、具备来源与时态治理、可逐步学习记忆策略的 Agent Memory 系统**，先真实接入当前企业多源问数/问答项目 Omni-Agent，再开展 Agentic RL（PPO 控制器与后续开放权重模型 SFT/GRPO）实验，最终成为可持续迭代、可演示、可复现、可写进技术简历的作品。

**主线闭环：真实多源任务 → 事件及来源记录 → 可信记忆构建/召回 → Agent 行为改变 → 独立任务评价 → 学习与演化。**

排序原则：**比赛可用与安全 > 可验证效果 > 可学习性与算法研究 > 通用框架包装。**

## 1. 项目目标：三个时间尺度

### 1.1 短期：服务当前比赛
- Omni-Agent 当前面向“中国电子杯”赛题八，重点包括 NL2SQL、Schema Linking、文档问答、跨源推理、多轮澄清、结果可解释性。
- 记忆必须帮助解决真实任务：跨会话业务术语/指标口径复用、经验证的查询/跨源方法复用、范围与版本变更后的安全处理。
- 优先复用现有 `ConversationStore`、`ConversationSourceStore`、`OmniAgent.query()`、规划与 `DependencyAgent` 执行链路；保持 SQL 只读安全、来源 SHA/版本校验及用户确认机制不退化。
- 保持当前比赛 Demo 独立可运行；任何新记忆能力都可以通过 feature flag 关闭并恢复原行为。**严禁把记忆文本直接当可信 SQL 或绕过现有执行校验。**

### 1.2 中期：完成可信的 Agentic RL 实验
- 参考 MemSkill 的**记忆技能选择与演化**，首先训练轻量 PPO Actor-Critic Controller，而非宣称已经微调生成大模型。
- 研究哪些记忆值得写、什么时候更新、哪些任务经验值得召回；以**后续真实 Agent 任务表现**定义价值，而非存了多少条或是否调用成功。
- M1 的固定策略和可验证评测先成立，再进入 M2。不能为了使用 PPO/GRPO 而改变任务定义或制造数据差异。

### 1.3 长期：简历、实习和可持续维护
- 项目对外能说清楚：业务问题、架构、个人工作、训练对象、基线、具体实验增量、成本、安全边界。
- 在有前期实证后，再对开放权重的**特定决策模块**做 LoRA SFT → GRPO（必要时租用多 GPU）；与 Controller PPO 严格区分。
- 逐渐形成通用 Python Memory Core + Omni-Agent Adapter + 可选 DSH/MCP Adapter。**DSH 适配不是当前比赛的前置任务**。
- 不将论文结果、先前教学 CRM 项目的结果写成 Omni-Agent 的真实成绩。第三方项目仅作为研究依据。

## 2. 当前事实与资产边界（2026-10-09）

### 2.1 Omni-Agent 是实际接入对象
- 当前 GitHub 项目是 Python/FastAPI 业务系统，不是 DSH 项目。
- 已有会话、来源指针、待澄清任务、SQL/文档执行、部分持久化与多轮逻辑；“新增记忆”不能重复造轮次历史或破坏已核实的来源继承。
- 历史评测与开发题的结论属于对应提交/配置；新实验必须说明代码版本、模型、题集及实际调用次数。
- 团队仓库 `main` 不能由本记忆研究直接修改；在已存在的远程 `memory` 分支开发，后续合并必须经用户/团队确认。

### 2.2 QiMem 是旧比赛资产，不是要原样迁移的应用
- 可优先复用的能力：分层记忆条目、证据/来源、版本与时态、作用范围、可靠事件处理、检索接口、经验提炼设计。
- 必须审查再决定复用：与麒麟 SDK、`kylin-real`、DSH v3 JSONL、Linux 专用接口及旧文件操作技能紧耦合的部分。
- 提取可移植服务契约；不能无依据复制、重写或把 QiMem 已实现能力说成“经过本轮训练学会”。
- 若 Codex 的执行环境尚无用户提供的 QiMem ZIP/路径，明确报告缺失；不得假设它已经在 Omni-Agent 仓库中。不得提交旧比赛敏感数据、完整个人历史或私有凭据。

### 2.3 已完成的基础训练学习
- `trl-learning` 教学项目完成过专家 SFT、真实工具环境 GRPO、Reward Saturation 和独立评测；可复用实验工程经验。
- 上一阶段 CRM 实验不是这个项目的算法基线，也不是本比赛的最终产品方向；**暂停继续扩展 CRM 教学环境**。

## 3. 拟议产品架构（实现以源码审查为准）

```text
Omni-Agent / FastAPI
  ├── 现有会话与来源管理、意图规划
  ├── 现有 SQL / 文档 / 跨源安全执行与答案验证
  └── Memory Adapter [默认关闭 / 可撤销]
       ├── recall(context, scope, budget)  →  有证据的候选记忆
       ├── observe(event, verified_outcome) →  可审计的事件/候选经验
       └── feedback(task_id, outcome)       →  经独立验证的结果
                ↓
        Portable Memory Core
        ├── Memory Store（语义/经验、版本、来源、作用域）
        ├── Retrieval（相关性+有效性/权限/时态过滤）
        ├── Ingestion & Governance（脱敏、去重、置信、更新、过期）
        └── Audit / Replay（可复现轨迹与决策记录）
                ↓
        Optional Learnable Policy（M2 后才引入）
        ├── Memory Skill Bank
        ├── PPO Controller：选哪些技能/记忆操作
        └── Designer：基于开发集失败归纳技能变化
```

**第一版仅有 Adapter + 最小 Store/Retrieve/Observe；不引入 Designer、不重构核心 Agent、不整体移植 DSH。**

### 3.1 第一版应处理的记忆
1. **业务语义与已确认指标口径**：别名、统计口径、单位、条件、适用范围；必须有确认或可核验来源。
2. **经验证的任务经验**：Schema/跨表关联风险、成功的证据获取顺序、澄清边界、错误原因、可复用方法；经验只提供建议，不能当作可直接执行的旧 SQL/结果。
3. 多轮临时状态仍优先由现有会话系统管理；用户偏好画像、任意事实百科、复杂忘却规则暂不是 M1 主目标。

### 3.2 记忆条目建议字段（具体以复用代码/API 审查调整）
`memory_id`、`memory_type`、`content`、`scope`、`provenance`（来源与证据 ID）、`source_version`、`valid_from/valid_to`、`created_at/updated_at`、`verification_state`、`task_trace_id`、可选 `cost/usage`。

约束：用户/项目隔离；不可将外部文档指令提升成 Agent 系统指令；旧来源或版本失效时拒用或要求重查；失败轨迹不能因工具返回“success”就晋升为可信经验；清除/撤销及版本恢复必须可审计。

## 4. 分阶段路线与进入条件

### M0 / M1-A：接入前审计与真实任务基线（最先执行）
- 以 `memory` 分支最新代码为准，确认 `OmniAgent.query()` / `_query_turn`、会话、来源、trace、实际部署方式与 QiMem 可移植模块。
- 输出“现有功能—记忆增量—具体接入点”三列表，不在确定接入点前大规模重构。
- 选取小规模**已曝光开发题**进行无记忆基线、失败归因与“提供合法正确经验”的 oracle-memory 上限诊断；测哪些任务真有记忆改善空间。
- 固定任务、模型、工具/Schema/文档版本、解码及预算，保存完整轨迹。不要改/偷看正式测试题，也不要把 oracle 内容写入待验证产品库。
- 交付：简明架构审计、基线配置和任务清单、典型失败/可改善实例。

### M1-B：最小可关闭的端到端记忆集成（近期主任务）
- 不修改现有 SQL 安全校验、来源审计和权限约束。
- 实现最小 `recall` / `observe` / `enabled`：规划前给出短且可溯源的有效候选；完成后异步或可靠地记录验证后的知识/经验。
- 先做测试：跨会话读取、相互隔离、重启后恢复（若声明持久化）、版本变化后拒用、无关问题不误召、服务失败退化为现有行为。
- 用相同开发题对比三组：无记忆、固定策略记忆、oracle 经验上限；任务正确率/任务完整性/来源正确性/误用率/工具调用/Token/时延都报告。
- 第一版的“完成”不是通过几个单测，而是至少有**可复现、可解释的真实端到端行为改变**；正向效果不保证，若无收益要定位真正瓶颈。

### M2：学习记忆选择策略（明确经用户批准后启动）
- 先固定 `Executor` / 记忆生成 LLM、技能内容、检索和基本记忆存储，训练轻量 PPO Actor-Critic Controller 选择记忆操作/策略。
- 状态由当前交互、已有记忆和任务上下文组成；动作是技能选择/记忆处理决策；奖励由后续任务的独立验证反馈定义。
- 对照：无记忆、固定技能规则、PPO Controller（固定 Skill Bank）；等 Controller 有可信收益后，再加入 Designer 学习技能演化。
- 记录 PPO 的 Action LogProb、Value/GAE、KL、Clip Fraction、Entropy、训练曲线和真实业务改善；**不能将 Controller PPO 写成 LLM GRPO 微调**。
- 验收：冻结模型/预算下，记忆质量或实际任务表现有增量；保留没有改善的结果和跨 Schema/跨会话的失败样本。

### M3：开放权重 LLM 的策略微调（明确经用户批准后启动）
- 基于 M1/M2 暴露的真实失败，选择**一个**可替换的规划/纠错模块。先 SFT warm-start，再 GRPO 等在线策略优化。
- 训练对象是开放权重 3B/7B 等模型，不能对现有远程闭源模型宣称完成参数微调。
- 同初始化模型对比 SFT 与 SFT+GRPO；另外比较是否启用记忆，分离 RL 增量与记忆增量。
- 保持独立环境、工具 Observation Loss Mask、奖励状态校验和真实 GPU 计时；不要反复用测试集调参。
- 先单 A100 做小规模运行/显存/梯度验证；增加算力只用于已通过机制测试的实验，不先租卡再寻找问题。

### M4：长期拓展（不是当前开发任务）
- 多用户隔离、权限与审计强化、持续学习的时间/版本冲突、受控技能演化、跨领域迁移、调用与记忆压缩成本。
- Python Memory Core 稳定后可做 DSH / MCP 通用适配及对外文档；不要为了宣传“通用”而牺牲比赛效果。
- 条件成熟后整理开源/演示、可靠 benchmark 与可审查简历项目条目。

## 5. 研究问题与评测纪律

### 5.1 核心研究问题
**在相同基础模型、工具、数据和上下文预算下，带证据与时态约束的可学习记忆策略，能否比无记忆或固定记忆策略更准确、更安全、更经济地完成未见过的企业多源任务？**

### 5.2 关键指标
- 主要：端到端任务成功率、SQL 执行结果正确率、跨源必要证据覆盖、澄清正确性、多轮有效约束继承。
- 安全：错误来源/过期经验使用率、跨作用域记忆访问、错误继承、无授权写入/错误 SQL 执行。
- 效率：每任务实际模型调用数、输入输出 Token、工具调用、端到端延迟、记忆库体积和检索延迟。
- 学习：更新了哪些参数、有效优势/奖励差异、训练曲线、随机种子及多次实验可比性。
- 统计：独立任务维度的配对提升/退化；不要用同一长对话的多个问题假装都是独立样本。

### 5.3 评测守则
- 公开数据和比赛本地题须记录来源、哈希、划分、可公开性与许可证。
- 只在开发集上调结构/Prompt/策略；正式测试冻结后一次执行；不可将测试答案写入记忆、技能库或 Designer 失败案例。
- 无记忆、固定规则、学习策略应尽量使用相同模型、数据初始状态和 Token/工具预算。改变多处时明确标记无法做因果归因。
- 工具返回成功不等于答案正确；实际来源和数据库状态优先于 Agent 的自我描述。
- 报告有局部开发改善但正式未测时明确说明；不得将论文数值、他人 baseline 或历史固定题成绩写为自己新结果。

## 6. ChatGPT × Codex × 用户协作协议（强制）

### 6.1 决策责任
- **用户：产品目标、比赛范围、时间/费用、是否启动新阶段及最终接受。**
- **ChatGPT：技术大脑/导师。** 读取仓库最新提交与原始日志，选择问题、提出假设、设定对照与阶段验收、解释 PPO/GRPO 等知识、根据真实结果决定下一轮；对不确定实现要求 Codex 去确认源码。不会只根据 Codex 的口头“已完成”判定实验通过。
- **Codex：执行工程师。** 阅读代码、实现、运行、测试、采样、归档证据、分析失败、提交并推送；对异常给出客观证据及 1–2 个方案，不越权更换研究路线。

### 6.2 分支与提交
- **只使用既有远程 `memory` 分支（小写）**；不得新建大小写近似分支；不得 push/merge 到 `main` 或改动队友分支。
- 每完成一项可验证的小成果（审计、最小接口、回归测试、真实对照）即 `commit` 并 `push origin memory`；不要囤积至最后。建议持续工作每 30–45 分钟至少推送一次有意义的进度或报告，结构性卡点立即提交诊断/说明。
- 单元测试或真实模型运行失败时保留日志，如需 WIP 提交明确标记 `WIP` 与未通过项，不伪称完成；失败不能通过重写历史结果掩盖。
- 每次反馈要包含完整 commit SHA、变更文件、确切运行命令、测试结果、原始日志/报告路径、剩余风险、建议的下一步。
- 用户和 ChatGPT 可以从 GitHub 的 `memory` 分支直接核对变化；无法访问 GitHub 时不得宣称已推送。

### 6.3 长期文档协议
- **本文件 `docs/MEMORY_RL_MASTER_PLAN.md` 是战略主线，未经用户/ChatGPT 明确批准，Codex 不修改目标、阶段边界或研究主问题。**
- Codex 在 `docs/memory_rl/` 下维护：
  - `STATUS.md`：当前阶段、最新 SHA、已完成/进行中/阻塞、下一项待决策；
  - `CODEX_REPORT.md`：每次关键执行的事实、改动和失败；
  - `EXPERIMENT_LOG.md`：数据、模型、命令、seed、预算、指标与原始结果路径；
  - `DECISIONS.md`：用户/ChatGPT 批准的关键决策、日期和原因。
- 只有测试真正执行后才能填写对应“通过”；不能用文档叙述代替实际运行。
- 每次新对话如果上下文不足，ChatGPT 优先读取本主线及 `STATUS.md`，再检查最新 commit 与原始报告；以 GitHub 可核验内容为准。

### 6.4 工作节奏与停止规则
- **禁止未经用户与 ChatGPT 批准直接从 M1 跳到 M2/M3**，或先行启动大规模 GPU 训练、改变正式测试规则、重构主 Agent 架构。
- 接口及业务实现优先选择简单的可验证方案，不以架构名词堆复杂度。
- 遇到结构性依赖/环境障碍，约 20–30 分钟内应得出复现与替代方案，停止无目的反复尝试；但不把一切正常失败都变成层层审批的阻塞。
- 用户时间宝贵：每次迭代必须交付**新的可核验代码或数据现象**，并能支撑一个明确的新认知；避免数小时仍只停留在安装/概念。
- 机密/个人数据、API key、`runtime/`、训练权重与大型语料不得提交公开仓库；如需复制 QiMem 源码先审查权限和许可证。

## 7. Codex 当前唯一授权的第一项任务

**M1-A：读源码、固定最小基线、设计可控接入点；然后在同阶段内逐步实现 M1-B 的最小开关/接口与少量集成回归。**

执行顺序：
1. 确认 `git branch --show-current` 是 `memory`；检查工作区和远程同步，保护队友与历史提交。
2. 阅读本主线、仓库 `AGENTS.md`、相关后端与已有测试；寻找真实记忆/来源集成点，别重复造已存在的会话历史机制。
3. 如果 QiMem 原始文件没有在 Codex 可见环境挂载，立即报告需求的文件位置；**不得假设它已在 Git 仓库**。没有 QiMem 时仍可做 Omni 审计和无记忆 baseline。
4. 先提交简短架构审计和 baseline 清单并 push；**这里先给 ChatGPT 一次审核机会**，避免直接改造错误调用点。
5. 审核后，用最小独立模块实现记忆开关/`recall`/`observe`，保持既有行为默认不变；小批次提交；测试通过后再用少量固定开发题做有/无记忆对照。
6. 只做 M1；本轮不实现 PPO、Designer、LLM GRPO、DSH 插件或跨仓库大规模迁移。
