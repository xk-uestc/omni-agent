# 延迟优化验收（2026-10-07）

12个相同合成数据库问题、两个独立请求并发，公网完整响应平均耗时从 14.72 秒降至 2.16 秒。12/12与独立只读SQLite查询一致。15个连续追问15/15通过，平均 3.23 秒。此为项目样例实测，不是一般问数性能保证。

主瓶颈为每轮真实模型SQL提议：例如华东采购金额15.09秒，其中模型规划12.37秒。启用ICT8_FAST_SQL=1后，在当前执行快照内完整规则覆盖的单表汇总/分组/排名/趋势和已配置派生指标直接使用规则计划。必须无澄清、无未覆盖词、无忽略指令、无关联/扇出/HAVING/同比；复杂关系和跨源约束继续真实模型提议及现有校验。

规则快速计划仍通过现有SQL编译、只读执行、结果预算、来源版本、来源表与历史签名流程。不复用旧答案，不扩大资源预算。审计明确 planner_source=server_verified_fast_rules、model_called=false，不能把此路径当作模型实测成绩。

普通模型演示启动tools/run_server.py --with-model默认启用，可通过ICT8_FAST_SQL=0恢复原路径。独立引擎默认不启用，原模型验收工具不会自动变成规则验收。

证据：runtime/speed-before-20261007.json、runtime/operations-demo-live-20261007.json（本轮快速路径）、runtime/speed-followups-20261007.json、runtime/speed-summary-20261007.json。原本的数据扩充验收说明对应初始模型运行；本轮报告明确改变执行策略。

RAG、扫描件与复杂联表仍依赖模型，耗时不保证降低到2秒。公网请求时间也受网络和上游服务波动影响。

## 2026-10-08 RAG 上游竞速复测

根因由同规格25轮报告和 Responses API 审计确认：SQL 快速路径多在1秒左右；慢 RAG 请求的 HTTP 总耗时几乎由模型 API 等待构成。原报告中政策 RAG 组中位数73.425秒、单轮最高131.160秒；T5 单次 `omni_plan` 用时59.151秒。RAG 另外会顺序执行 grounded answer、必要时 correction、span selection 和独立 review。后续步骤依赖前一步的输出，调用耗时相加；换 API 只能缩短每次等待，不能消除这条串行链。

已启用四端点 Responses 池：原 `gpt-6-luna` 保留，用户提供的 `gpt-5.6-sol` 和两路 `gpt-5.5` 作为备用。先发当前延迟评分较好的端点，2.5秒无响应时启动一个备用；最多两个端点同时请求，其他备用在前序端点失败时接力。带备用配置时每端点只做一次传输尝试，单端点超时封顶30秒。响应必须通过端点配置对应的模型身份检查和原有 JSON Schema/答案证据校验，不能因 HTTP 200 就直接发布。实际胜出模型和每次竞速记录保存在请求审计里。

Conpera 的 `service_tier=fast` 已按请求字段发送，并通过最小结构化响应探测（HTTP 200、指定模型身份和 JSON 形状均通过，约2.91秒）。其他备用未设置此参数。

Dense BGE 编码器原本在首次用户查询时才加载。当前知识库有218个 chunk，向量缓存已有341项；首次编码器初始化在首问增加约9.7秒。现改为服务启动时补齐缺失向量并预热查询编码器。完成预热后首个政策问答从22.557秒降至10.888秒；两者 API 调用合计约12.8秒，因此该前后比较同时受上游波动影响，不应把约11.7秒差值全归因于预热。

**结论：** API 竞速显著压低了尾延迟，但速度问题尚未完全解决。最终25轮里最慢仍30.427秒；该轮及相邻慢轮包含5次串行模型调用，审核链而不是前端渲染或普通SQL查询仍是主要剩余成本。下一步若继续压低RAG耗时，应减少重复的串行生成/投影/复核调用，同时保留可验证的原文引用和整题覆盖约束。本测试使用项目合成样例，不代表任意问题或公网负载下的普遍准确率/耗时。
