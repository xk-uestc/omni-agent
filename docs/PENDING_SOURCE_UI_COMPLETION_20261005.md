# 待补任务的页面选项完成与数据源校验

## 真实缺陷及修复

页面选择选项通过`/api/v1/omni/clarify`提交补全后的完整问题。完整文本原先被作为独立问题保存，虽SQL成功，旧待补编号仍能恢复。新增端到端回归首先复现`missing_time_grain`而非预期完成状态，失败证据保留在开发输出。

修复后，澄清接口完成选项/原问题/当前会话状态核验，再传递仅服务端可设置的`_confirmed_pending_turn_id`。普通SQL的后续待补状态与完成状态关联原任务；比较澄清继续使用原比较流程，不被合并为普通SQL任务。文本回复与页面选择均完成相同生命周期。

## 独立Agent校验

`PendingSourceValidationAgent`只核对来源和判断追问是否依赖旧问题，不执行SQL、不生成答案。

- 每个新SQL待补状态保存`engine.current_source_revision()`；使用数据库文件/WAL代际、schema版本和取值别名内容的现有来源代际定义，不冒充全库内容密码学哈希。
- 正常恢复或保留澄清时继承原绑定，不通过重新盖章掩盖来源变化。
- 数据库内容更新、相同Schema换库、业务映射变化或缺少旧版绑定时，依赖旧条件的短追问/帮助/条件修改需重新确认。
- 明确完整新查询仍可在当前数据源重新规划，不因此全局锁住会话。
- 同时包含日期和指标的复合修改仍属于修改指令，不能借“看似完整问题”跳过来源检查。
- 页面旧选项返回409；明确旧编号恢复返回`pending_reference_source_changed`。文本补充返回`pending_source_changed`，页面过程展示“核对待补问题的数据来源”。

这是会话范围的来源核验，不声称解决外部数据库并发变更的分布式快照/CAS问题。未升级的无绑定旧待补需重新提交原问题。
