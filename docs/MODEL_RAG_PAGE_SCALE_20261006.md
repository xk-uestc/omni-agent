# 真实模型 RAG 三规模性能复核

依据官方决赛评分表“系统效率设计与伸缩性证明”，补充检索到真实模型答案的端到端样本。报告：`MODEL_RAG_PAGE_SCALE_ROUND30_20261006.json`。仅使用 gpt-6-luna / medium；Windows 11、Python 3.12.10、20 逻辑线程，本地 BGE-small-zh。与其他回归/模型任务同时运行，不是独占硬件峰值测试。

## 实测

复用现有合成中文合同 PDF 生成器；三规模新建独立知识库，不复用旧索引。问题带唯一 CASE 编号，经过生产 `KnowledgeStore.answer`，没有向模型提供参考答案、正确页码或 document_id。每规模冷请求 1 次、1/2/4 并发各一组，共 8 次、合计 24 次真实问答、72 次模型调用，起止后端源码一致。

|页数|片段数|解析入库 ms|首次答案秒|1/2/4 并发完成 QPS|4 并发单请求中位秒|
|---:|---:|---:|---:|---|---:|
|10|50|293.7|18.04|0.0952 / 0.1454 / 0.1118|22.52|
|100|500|396.1|9.79|0.0994 / 0.1652 / 0.1008|25.94|
|500|2500|1211.5|14.59|0.0874 / 0.0433 / 0.0634|60.76|

24 次均返回 status ok，且实际回答字面与合成参考值匹配、引用预期原页和源 SHA。这是此性能场景的值/来源诊断，不是多文档问答正确率，更不是官方 RAG 90% 成绩。失败请求会保留在分母中；本次没有鉴权错误。

各规模模型请求审计耗时之和分别占问答耗时总和 94.2% / 96.9% / 90.9%。该比例包含远端请求及网络等待，不等于服务商 GPU 推理时间。500 页 4 并发比低并发慢，不能声称增加线程必然提速。

## 链路复杂度与边界

- 意图/答案模型：输入在各链路既有预算内；实际计算复杂度取决于远端模型结构、输入/输出长度，不能用本地页数断言其时间复杂度。报告逐请求保留 token、调用数和请求耗时。
- 数据定位：`knowledge_store.records()` 会读取并反序列化全部 M 个片段，总时间/空间至少与总片段文本量成正比。CASE 编号过滤也需遍历这些记录；本次不是全文 dense 排序的规模证明。
- 检索：无编号的完整向量路径，现有 `dense_retrieval.DenseIndex.search()` 做 M 个 d 维余弦相似度及排序，约 O(Md + M log M)，向量缓存 O(Md)。本次带编号请求在过滤后的较小候选集上检索，不能把 2500 片段数当成每次实际 dense 候选数。
- 原件定位/生成：仅将有界候选证据交给模型；源摘要、引用及完整问题校验仍执行。该控制限制模型输入，并不证明所有文档已经遍历或全语料语义完整。
- SQL、PDF 解析本地三规模证据见 `PERFORMANCE_SCALE_PROGRAM_20261006.json`；结构化真实 HTTP 三规模见 `MODEL_HTTP_ROW_SCALE_ROUND19_20261006.json`。扫描 OCR 不在此文本 PDF 测试中，OCR 对照报告单独保留。

## 并发与优化策略

本次证明这三种文本样本可完成 4 个同时在途请求，是已测并发下界，不是最大并发能力。正式 SSE 默认准入 16、视觉工作默认 4、文档解析默认 4；配置上限或允许进入数也不是持续服务容量。需要更长稳态、排队/超时/内存测量后才能估计最大容量。

现有措施包括内容版本向量缓存、编号精确筛选、模型输入去重、候选证据预算和独立客户端并行。Round28 原件模型上下文减少约75.5%输入token，但观测耗时未下降，不能计为速度优势。当前实测主要等待在远端模型请求，下一步优化应先减少重复必要性不足的调用，同时保持原件/整问审核，而非继续堆线程或缓存未绑定的旧答案。

三规模证据比之前只测本地解析更完整；仍缺扫描 OCR 全链路、无编号语义问答并发、稳态最大吞吐等。效率分保守维持 3/5，不因新增报告自动计满分。
