# 赛题八：面向一等奖竞争力的优化建议与验收路线

审阅日期：2026-10-01。

依据：用户提供的《“中国电子杯”第三届高校 ICT 产教融合创新大赛赛题八：多模态数据驱动的可解释精准问数/问答智能体》，2026 年 5 月正式版，共 14 页；当前本地项目代码、已保存评测报告及只读接口检查。

审阅基线：Git HEAD `c993dfa`；本轮开始时 `ict-track8/frontend/index.html` 与 `app.js` 有上一轮已授权的未提交改动。本报告评测数字来自已有报告，本轮没有重新运行整套准确率评测。本轮实际检查了健康接口、Schema，并复现了一例公式抽取失败。

本文中的目标值、资源安排和预计收益均为建议，不是已经取得的成绩。赛题文件给出的是校内初赛与决赛小组赛评分，获奖等次依排名确定；后续阶段以组委会最新通知为准，不能由内部测试直接推算国家一等奖。

## 1. 判断与主攻方向

项目方向与赛题高度适配，已有值得继续投入的工程基础：真实 SQL 执行、字段与外键定位、只读保护、澄清接口、会话、流式过程、多格式解析，以及独立生产 RAG 的检索与证据组件。

当前主要缺口是：**复杂业务口径未形成统一约束，跨源查询还未形成真正的数据依赖计算，独立泛化和真实多模态证据不足。** 当前运行网页是规则规划器与小型行业演示库；应将它定位为可运行的工程基线。

建议作品的核心主张：

> 面向企业经营分析，把自然语言问题转成可确认的业务口径；让数据库、文档、表格中的事实共同参与计算；每个关键结果都能定位来源、解释约束并复算。

一等奖路线应形成一条完整主线：

**业务口径约束 → 泛化定位与复杂 SQL → 跨源依赖计算 → 结果逐项核验 → 可点击来源 → 独立评测证明收益。**

优先申报“实用创新与转化价值”；“技术突破领先性”需要同条件对比和公开基准证据，待实验成立再申报。统一证据、结构化计划和文档质量路由本身都有已有研究基础，不能仅凭名称宣称原创或领先。

### 3.1 两个现场能说明问题的例子

**业务口径无法闭环。** 当前文档写“已完成订单”“不含取消订单”，行业库的 `orders` 表却没有订单状态字段。没有数据集整体状态声明或额外字段，系统无法从现有 Schema 核验这一口径。这个现象尚不能证明当前数值错误，但足以说明“检索到了政策”不能等同于“SQL 已落实政策”。

**公式抽取边界有实际失败。** 本轮向 `/documents/analyze` 输入：

```text
毛利率 = (500 - 300) / 500
2.2 客单价
客单价 = 销售额 / 订单数
```

后端将第一个表达式抽成 `(500 - 300) / 500\n2.2`，返回 `rejected`；第二个符号公式抽取为空。这应列为第一批修复和回归例，不能把“有公式接口”写成“已解决文档公式计算”。

## 4. 第一优先：统一业务语义和查询计划

### 4.1 将业务口径写成可检查的数据

为指标建立小而明确的语义配置：指标 ID、展示名、公式、单位/币种、事实表、原生粒度、主体主键、时间口径、合法维度、包含/排除条件、有效期、来源版本、缺失值和零分母策略。

例如“净收入”需要明确：按下单、付款还是确认收入日期统计；退款按原订单期间还是退款发生期间冲减；是否含税；单位元还是万元。由文档提出的新口径要保留原文位置与有效期，再由校验器确认其适用范围。

先覆盖 8—12 个实际要演示和评测的指标，避免一开始建设庞大的企业本体。配置可由模型辅助草拟，关键口径需通过数据管理员确认或明确来源规则验证。当前库缺少状态、退款、成本等字段，应先补有来源的数据或显式标记无法回答，不能凭文档文字补造记录。

### 4.2 规则与模型输出同一份 QueryPlan

保留规则的低成本路径；扩展现有 QueryPlan，而不是另建一条绕过安全门的模型 SQL 通道。分批加入：

- `metrics[]` 与受控表达式树，支持多指标、比率、数值单位；
- 事实原生粒度、结果粒度、实体主键与 JOIN 基数；
- 明确的日期窗口、时区、粒度和口径版本；
- 受限的预聚合、EXISTS、窗口和子查询节点；
- 每项选择的来源：用户片段、确认过的语义配置、前轮状态或文档事实。

先补合同比/环比、Top-N、多指标和预聚合这些真实业务需求；更一般的嵌套/集合查询按独立错误分布决定下一步，不宜同时扩成无限制 SQL 语言。

### 4.3 在业务粒度上解决 JOIN 重复

两条订单明细连接三条退款记录，可能得到六行，直接 SUM 会重复统计。解决方式应是各事实表先聚合到约定粒度，再按验证过的键关联；只判断是否存在的条件使用 EXISTS。**不能用 `SUM(DISTINCT amount)` 当通用修复**，两笔金额相同的真实订单会被错误去重。

当前规则对一对多 SUM/AVG 会澄清，属于安全边界；需增加能正确完成这些题的路径，才能同时提高准确率和可回答覆盖率。

### 4.4 模型负责提出候选，独立检查决定执行

建议只允许 1—3 个候选计划。检查字段存在、实体取值有据、显式条件覆盖、粒度/单位一致、JOIN 关系、文档版本和 SQL 只读范围；有明确可修原因时允许一次有界修复，仍有业务歧义就澄清。

现有模型验证会要求新分组维度必须已被规则识别，规则的语言覆盖因此可能成为模型上限。应保留已确认显式条件的硬约束，同时允许通过用户片段、数据字典和有效语义定义证明的新解析。模型自报 confidence 或两个模型意见相同，都不能单独证明语义正确。

需先检查并补齐模型契约中的 `top_n`、`fan_out`：当前构造 QueryPlan 时未映射二者。Top-N 在后续又被要求与规则一致，存在必然回退的路径；模型与规则的扇出保护也需统一。这是静态发现，尚未据此断言已发生错误统计。

## 5. 第二优先：陌生业务的联合定位与精准澄清

### 5.1 联合考虑字段、取值和表关系

把“北京/帝都”映射到实体只是第一步，还要判断它属于客户所在地、订单归属地还是交付地。建议采用以下过程：

1. 数据接入时自动读取 DDL、外键、类型、注释、取值摘要、唯一性与分布。
2. 查询时按业务词与数据画像召回少量候选字段；语义召回可用于陌生词，但应保留精确词和数值匹配。
3. 查证实体取值，联合关系图排除不合理路径；对语义相近但业务角色不同的表保留候选。
4. 比较候选是否会改变实体范围、粒度或指标定义；无法确定时提出业务语言的澄清。

现有取值索引会跳过超过 5000 个不同值的列，应增加受限的索引查询策略，覆盖高基数客户、产品编号等场景。不要为每次请求加载整个取值列，也不要将大量样题塞入提示词。

证明低成本扩展的方法：在至少 3 个未见数据库上允许提供元数据说明，禁止添加目标测试问题对应的 few-shot；记录接入时间、人工标注量、字段召回率、路径正确率和复杂 EX。Chinook 已有相关画像/词典，不能直接当作完全未见领域。

### 5.2 澄清应减少真正的业务歧义

优先澄清会改变答案的决策。例如：“按订单归属地区，还是客户所在地区？”比“请补充维度”更可操作。候选模型可帮助识别歧义，但问题应由实际候选之间的差异生成。

澄清闭环使用服务端候选 ID 与槽位值，选择后更新已验证计划。复核所有 `clarification_code` 是否均有处理路径，尤其规划器能产生而 resolver 尚未覆盖的 `ambiguous_dimension`。

多轮状态保存当前确认的计划、实体集合引用、时间窗口、口径和版本；每轮记录“改地区、换指标、移除过滤、回到前一版本”等变更。这样才能可靠支持“只看刚才前五名”“恢复上一口径”“改成客户所在地”。表面上的文本拼接不适合继续承担复杂分析记忆。

验收同时看澄清方向准确率、一次澄清解决率、无谓澄清率和整段对话完成率；从“任意一段六轮成功”升级为独立多轮任务集全部统计。

## 6. 第三优先：真正的跨源依赖计算

在现有编排器上加入少量有明确输入输出的工具节点：检索、事实抽取、实体匹配、SQL、受控计算、核验。节点之间传递值、单位、时间、实体 ID 与证据引用，不传递一段无约束文本作为执行指令。

先实现这 6 类任务，每类建议至少 20 道独立验收题；“类型多”要体现依赖结构不同，而不是把华东换成华南。

| 跨源类型 | 业务例子 | 必须完成的依赖 |
|---|---|---|
| SQL → 文档 | 找出 2025 年销售领先团队并解释其方法 | SQL 实体 ID/别名驱动后续检索，并核对同名实体 |
| 文档 → SQL | 按某版政策找出符合返利条件的客户 | 提取有效日期、门槛和条件，再绑定到受控 SQL |
| 文档公式 → 多源取值 → 计算 | 用制度定义的公式计算净收入或毛利率 | 公式结构、各参数来源、单位、时间和舍入一致 |
| 数据库 ↔ 报表 | 对比数据库实际值与 Excel/PDF 目标 | 时间、组织和统计粒度对齐，解释差额 |
| 多版文档 → 口径选择 → 重算 | 对比新旧政策下的返利金额 | 按有效期选择版本，展示结果变化和原因 |
| 低质量图表 → 核验 → 回答 | 从扫描表读出预算，与数据库实际发生额比较 | 识别图/表，定位数值，质量不足则修复或澄清 |

给每个节点设置允许的工具、超时、最大结果规模和失败处理，先按依赖模板支持条件分支。无需先堆大量角色互相聊天；工具类型、数据契约与终止条件清楚更容易维护和评测。

### 必做的反事实验证

- 改变文档门槛，目标客户集应相应变化。
- 删除关键来源，系统应说明无法完成，而非继续报原答案。
- 更换政策有效期，只重算受影响时间窗口。
- 放入同名人员/相近字段，系统应正确对齐或澄清。
- 改变一个数值来源，只影响依赖它的下游结果。

这些试验可以直接证明系统确实使用了多跳证据，不是仅在答案末尾附了几份文档。

## 7. 最有辨识度的能力：每个数值都能核对和复算

统一事实记录至少包含：`value / unit / currency / entity / period / source_revision / locator / extraction_method / quality`。

来源位置分别使用 SQL 查询与结果行列、Excel 工作表与单元格、PDF 页码与区域、文档标题路径、图片区域。对模型抽取的事实保留原始证据，不能用生成摘要替代来源。

公式计算分三层：

1. **识别公式和参数角色**：区分“毛利率定义”“给定值”“待求量”“示例数字”，排除电话、日期和章节号。
2. **绑定事实**：每个参数必须与实体、时间、单位、币种、口径匹配；成本缺失时明确要求补充。
3. **确定性计算**：受控符号表达式树、Decimal、单位检查、零分母和舍入规则，输出可复算步骤。

优先修复已复现的跨行公式边界，再支持带单位的符号参数绑定。暂不追求任意高等数学公式识别；把返利、净额、客单价、毛利率等业务公式做好，更能证明实际价值。

每个最终结论携带引用清单和计算来源。核验器检查：是否覆盖了用户要求、证据是否适用、单位时间是否一致、公式是否可复算、数值是否来自本次执行。哈希与完整追踪只证明记录可核对，不单独证明业务解释正确，仍需要独立金标与人工评审。

## 8. 多模态与 RAG：用真实文件组成闭环

### 8.1 先形成完整资料包

官方第 9 页要求至少 10 份不同类型文档样本。建议选定企业销售/经营分析场景，准备 20—30 份有来源的资料：原生 PDF、中文扫描 PDF、DOCX 制度、Excel 台账/目标、图片表格/图表，包含少量相互冲突的版本和无法回答场景。

每份文件保留原件、来源或合成声明、许可/使用范围、版本、SHA-256、标注。若使用合成业务数据，明确说明，不包装成真实企业案例。已有生产 RAG 的真实资料可以复用，但必须确认在当前赛题交付范围内可重建且允许随包提供。

### 8.2 复用现有检索优势，补齐接入信息

接入 canonical RAG 的真实检索链，分别验证结构化查询、文档问答及混合问题。扩展适配器，保留完整证据 ID、原文定位、版本、表格/图像信息，以及真实 BM25/Dense/RRF/重排审计字段。当前只取短 snippet 的接口，不足以承担公式参数与原页引用。

主片段提供直接依据，辅助片段补定义、前置条件或上下文；在跨源任务中把证据角色映射到需要证明的具体结论。测量引用是否支持该结论，而非只测检索命中。

### 8.3 让质量分驱动实际处理

原生文字可直接读；低置信关键区域再 OCR；复杂表格走结构解析；公式区域单独识别；必要时用视觉模型复核。只有与本题相关且影响结论的区域进入昂贵处理，控制成本和延迟。

现有质量/复杂度分为手工加权，应以真实标注集校准：哪些分数区间更容易出现数字错读、标题错层级或表格断裂；所选修复是否提高了下游答案正确率。允许处理失败与人工确认，不强制把每页都“修复成功”。

单独评估中文/中英混排 CER、表格结构、公式等价性、参数绑定、目录层级和最终问答。英文合成模糊图的通过率不能代表中文扫描业务材料的可靠性。

## 9. 评测改造应先于下一轮大规模优化

### 9.1 修正判分口径

当前 `eval/run_eval.py` 有下列需要修正或分项报告的地方：

| 当前判法 | 潜在误读 | 建议 |
|---|---|---|
| 预期澄清时，返回错误 code 仍计 correct | 方向不对也被视为精准澄清 | 区分发起澄清与澄清正确；code 可等价归类但须有金标 |
| 在输出列中任意排列投影比较值 | 标签、单位错却数值碰巧相同 | 金标增加指标身份、单位/币种、时间范围、粒度与排序 |
| simple 子集包含整个 legacy 类 | 单表与复杂题可能混合 | 按实际 SQL 结构与业务需求重新标注 |
| 任意一个 ≥5 轮成功就映射参考满分 | 不能代表多轮稳定性 | 汇报全部对话的严格成功率和错误轮数 |
| case ID 哈希分 dev/test | 可能共享同模板、同数据库结构 | 按数据库、模板族、来源文件分组隔离 |

这些是评测规则的局限，不等于已经证明全部现有成绩无效；应保留原报告并用新口径复算、解释差异。

### 9.2 区分答案回放与泛化能力

生产 RAG 的 `api_server.py` 中存在默认可启用的 `BENCHMARK_ANSWER_FALLBACK_ENABLED`，其逻辑读取 450 源题/448 唯一问题的审核答案表并在精确命中时返回答案。

作为产品 FAQ 可单独评估；**正式未知问题能力测试应关闭该路径或将命中单列**，同时记录运行配置。本轮未证明历史评测使用过该路径，也不能把这个发现归因到当前规则 NL2SQL 的 100% 报告；它是后续生产 RAG 评测必须控制的条件。

### 9.3 建议的独立验收集

| 类别 | 建议规模 | 分割与判定 |
|---|---:|---|
| NL2SQL | 300 个独立任务，其中至少 200 个复杂任务 | ≥3 个异构业务库；留出完整数据库/业务角色；人工双审 SQL 与口径 |
| 精准澄清/多轮 | 40 组，每组 5—8 轮 | 指标替换、过滤增删、话题切换、用户纠错、结果集合引用 |
| 跨源依赖 | 120 题，6 类各 20 题 | 同时标注最终答案和必需中间事实、来源、单位 |
| 多文档/多模态 | ≥100 题 | 原文/扫描/表格/图像/公式，按源文档隔离 |
| 鲁棒性配对 | 从上述任务抽取 ≥100 对 | 错别字、别名、模糊、旋转、缺来源、版本冲突；不冒充独立新增题 |

官方建议优先使用 OHR-Bench、Chinook、AdventureWorks；可增加 BIRD/Spider 类公开题的适配子集检验不同复杂度。须说明子集选择、适配规则、数据许可证和是否已接触测试集；不能将子集分数称为完整公开榜单成绩。

封存金标，由未参与具体修复的人保管；开发只使用开发集，揭盲后的题转为回归集，下次验收换新题。重写一个旧题的措辞不自动构成独立盲测。

### 9.4 目标与衡量方法

下列是建议的内部验收目标：

- 独立复杂 SQL EX 达到官方 90% 门槛，争取 95% 留余量；同时报独立样本数和 95% 区间。
- 多文档/多模态最终答案正确率争取 ≥90%，分开列简单文字与图表/扫描难题。
- 在明确可回答集合上，覆盖率争取 ≥90%；静默错答率争取 ≤1%，并报告小样本不确定性。
- 澄清方向准确率和澄清后任务完成率分别争取 ≥90%，对话以全部轮次成功为严格口径。
- 数值引用定位、参数绑定与可复算比例单列，不允许缺引用的正确猜测自动通过证据验收。

避免通过大量拒答提高“已回答题正确率”；同时绘制覆盖率与错答率关系。对数据库变体、多轮和同一原文扰动按任务/来源分组统计。小样本中零错误也不等于真实错误率为零。

### 9.5 有说服力的对照与消融

在相同数据库、模型版本、上下文预算和硬件下比较：

| 实验组 | 回答的问题 |
|---|---|
| A：当前规则基线 | 现有工程能做到什么 |
| B：模型直接生成只读 SQL，经过相同执行保护 | 单纯更换模型能做到什么 |
| C：模型输出统一计划＋校验 | 计划约束是否减少静默错误 |
| D：C＋业务语义/粒度配置 | 指标口径、扇出、单位错误是否减少 |
| E：D＋字段/值/关系联合定位 | 陌生 Schema 和相近表是否改善 |
| F：E＋跨源依赖计算与逐项证据核验 | 文档是否真正影响数值，跨源答案是否更完整 |

对多模态另做固定解析与质量路由、纯文本与坐标/结构、无参数核验与有核验三个配对对照。不必把所有组合全排列；只比较能回答核心贡献的问题，记录失败样例和费用。

## 10. 前端应帮助评委判断“为什么可以信”

Lattice 外观已形成，接下来恢复和补齐真实数据驱动的解释层：

1. **问题与口径**：高亮指标、时间、实体、条件；显示本轮改变了哪项上轮口径。
2. **表与路径**：从实际 Schema 与已验证 plan 绘图，高亮字段、连接键、关联基数；区分备选路径与最终路径。
3. **跨源步骤**：实时展示先后依赖、输入输出引用、耗时与等待澄清状态。
4. **结果与图表**：指标单位、统计范围、空结果与未知分开；表格与图表由同一结果集生成。
5. **可点击来源**：点击数值打开原页框选区域/Excel 单元格/SQL 行列；公式显示实际绑定参数和确定性计算。
6. **文件入口**：真正上传 PDF/图片/表格，自动质量检查并显示增强前后对照；手工质量信号仅作为开发调试入口。

当前新页面只处理 SSE trace/done/error，应接好已有 audit 事件与来源快照，保证中途到达的证据及时展示，最终结果不会覆盖掉先到的详细字段。

展示可核对的执行记录和决策依据即可，不需要生成长篇“模型内心思考”。日志 JSON 保留为高级详情，主界面用业务语言与图形表达。

## 11. 性能、部署和材料

### 11.1 性能证明

现存毫秒级数据主要是 SQLite/文本分析局部基准，文档本身已注明不含模型、网络和 OCR；不能改称整套问答时延。

按官方第 13 页准备 1k/10k/100k 行与 10/100/500 页三种规模。分开测文档入库、索引构建和在线查询，避免把离线 OCR 时间隐去，也避免每次在线查询重复算整本 PDF 的解析时间。

实际 HTTP 链路记录：冷启动与热缓存、P50/P95/P99、正确完成的 QPS、超时率、并发 1/4/8、峰值内存/显存、模型 token 与费用、CPU/GPU/内存/软件版本。错误、快速澄清、取消与正常答案分类；不能把快速拒答当作成功吞吐。

用测量选择缓存、索引、候选 Schema 缩小、局部 OCR、独立节点并行。缓存键包含数据/文档版本、业务口径与权限，避免以旧答案换取低延迟。真实执行器无法处理的任务应给可理解错误和恢复路径。

### 11.2 可交付性

准备可重建的代码环境、数据库 Schema、演示数据及原始文档、版本化配置示例、快速启动、运行自检和明确外部依赖。提供在线模型模式与能力边界清晰的本地演示模式；演示结果中标记实际来源，不把失败切换伪装为正常模型推理。

源码包和证据包分别建立 SHA-256 清单。当前打包脚本会排除 SQLite 和生成报告，源码可重建包不能自动等同于包含数据与验收证据的完整竞赛 ZIP。正式交付应包含生成数据脚本/所需数据、原件样本、金标/报告、运行步骤和许可说明。

### 11.3 决赛材料

- 深化技术文档：Word 与 PDF 各一份，建议不超过 50 页。
- 答辩 PPT：建议不超过 20 页，不出现单位、人名等识别信息，以主办模板为准。
- 创新自述：PDF，不超过 5 页，说明申报方向、核心贡献、对照/消融、场景价值和局限。
- 最终代码数据 ZIP：全量必需材料及环境配置。

答辩重点用一个复杂任务串起方法，并用消融解释增益来源：哪些错误以前会发生，现在哪个约束发现并解决了它，代价增加多少。展示一条正常完成链和一条歧义/冲突恢复链，再让评委临时换地区、时间或政策版本。

## 12. 可执行的推进顺序

以下按 2—3 人小团队、约 4 周有效开发时间估算，仅用于安排优先级。截止时间、模型预算和数据授权确定后需再调整。

| 阶段 | 交付物 | 退出条件 |
|---|---|---|
| 第 1—2 天：可信基线 | 运行清单、严格判分、旧报告归档、演示库/政策口径差异表 | 已知宽松判分与公式边界问题被列入可复现验收；新成绩有清晰分母 |
| 第 1 周：完成一个垂直任务 | 真实资料包、模型/OCR可运行、指标语义配置、统一Plan、参数化执行 | “政策决定口径→查数→公式→来源定位”能端到端跑通 |
| 第 2 周：复杂与跨源扩展 | 多指标/粒度、6类依赖任务、候选澄清、多轮状态 | 不同路径与失败边界均有任务金标，未靠添加答案完成 |
| 第 3 周：独立验收与优化 | 封存新题、消融、陌生Schema、真实扫描、三规模性能 | 明确达到哪些官方门槛；重点消除静默错答，未达部分如实说明 |
| 第 4 周：冻结与交付 | 完整运行包、证据包、技术报告、匿名PPT、创新自述、现场演练 | 换一台干净机器能重建；临时问题与异常恢复可演示 |

若只有 7 天，收敛为：严格评测 + 真实模型/OCR接通 + 一个跨源计算任务 + 五项已有中级能力的扎实例证。不要同期开多个全新行业、通用自动训练、多智能体团队和分布式平台。

建议分工：一人负责语义/SQL/澄清，一人负责文档/证据/前端，一人负责独立数据标注、评测、部署和材料。金标保管与针对失败的实现应尽量分离。

## 13. 下一步最值得做的一件事

选择一个问题完成所有证据，而非分别演示许多孤立模块：

> “按 2025 年生效的制度，计算华东各渠道已完成订单扣除退款后的净收入与毛利率，对照目标说明差异，并指出采用了哪些条款和数据。”

该问题是**建议新增的验收场景**，当前数据库缺少状态/退款/成本/目标等必要事实。实施前先用许可明确的真实数据，或公开标记的合成数据补齐对应 Schema 与文档。

它同时检验实体/字段定位、政策有效期、复杂 JOIN、退款粒度、公式参数、业务单位、跨源比较和来源核验。第一次只做一个渠道与一种政策；可复算且反事实检查通过后，再扩到多渠道、新版本和扫描附件。

建议先提交五类边界清楚的改动：

1. 评测口径与复现缺陷修正。
2. 统一指标语义与 QueryPlan 契约。
3. 跨源依赖执行和事实/公式绑定。
4. 真实文件及前端来源定位。
5. 独立验收、消融、性能与交付。
