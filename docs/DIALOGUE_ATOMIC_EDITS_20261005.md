# 连续对话：成功查询多条件修改与序号补选

本轮改进普通 SQL 连续对话与比较子查询的补选体验。目标是明确修改能完整继承原范围、非法修改不破坏已成功上下文；不宣称任意自然语言对话已完成。

## 新行为

- 成功查询后支持命名条件修改，例如“时间改成2024年，地区改成华南，指标改成订单数”。最多四分句，160字符，先构造全部候选并核对，再进入正常查询执行。
- 支持成功查询后的精确筛选增删，例如“增加渠道筛选为线上”“删除渠道筛选”。使用当前数据库字段与真实取值，不限于写死地区或渠道。
- 一项未知、同一项重复修改、非法时间或额外语义无法核对时，整条修改拒绝。原成功查询仍为下一轮可引用上下文，没有部分执行、没有创建伪成功查询编号或污染比较来源。
- 原 SQL、参数、来源版本、执行记录摘要与独立重解析条件全部核验；数据变化、缺记录或字段条件篡改不能授权修改。原查询的分组、排序、排名、比较及未指定筛选都必须保留。
- “选第二个”“选择第2项吧”“最后一个”“选2”可补选当前菜单。单独“2”不当作选项，带额外条件的句子不截取成单选。
- 序号绑定此前实际展示的完整选项顺序，并重新解析当前条件验证选项。旧会话缺少菜单快照、菜单变序、越界或数据来源变化都不能猜选；重新展示可选项后再选。
- 选择年份／月份类型仍需要填写具体时间，不能自动填今年。待补菜单编号支持 SQLite 重建后继续，比较对象的待补查询复用同一补选处理。
- 两个前端入口给条件选项显示一致的一起始编号。修改拒绝时输入框保留上一条成功查询的状态，回答说明整条修改未执行，可以纠正后继续。

已有简单“那华南呢”“换成订单数”路径继续使用原独立验证器；本轮新增分支限命名修改、筛选增删和多分句。按明确编号返回旧 SQL 查询也可使用这些修改。重置、其他会话和失败执行不借用成功结果。

## 实现

- `backend/executed_scope_edit.py`：验证已执行上下文、原子修改与未修改条件保持。
- `backend/pending_scope_edit.py`：抽取命令识别与无状态条件修改器，待补任务和成功查询共用。
- `backend/sql_history_scope.py`：成功查询修改与当前菜单顺序补选，不绕过正常 SQL 检查与执行。
- `backend/clarification.py`、`clarification_continuation.py`：序号解析、越界和需补具体时间说明。
- `backend/pending_source_validation.py`、`omni_agent.py`：来源变化拒绝、菜单快照和修改失败保留上下文。
- `frontend/conversation-context.js`、`app.js`、`knowledge.js`：菜单编号、条件变化与拒绝后的输入框状态。
