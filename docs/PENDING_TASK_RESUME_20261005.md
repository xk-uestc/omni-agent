# 被其他话题打断后的待补查询恢复

## 独立恢复Agent

新增PendingTaskResumeAgent，明确解析“继续/恢复/回到待补查询编号q_...”及可选的同轮补充内容。编号选择的是当前会话保留的一条尚未执行SQL的澄清快照，不是最近一次成功查询，也不自动选择看起来相近的任务。

选定记录必须唯一、属于SQL待补问题、没有执行记录或比较快照；待补问题文字、澄清类型、筛选、指标和分组必须与当前重新解析一致。读取历史不赋予SQL执行资格。纯恢复返回当前选项、不调用模型、不执行SQL；恢复后下一条补充使用该完整问题。

同轮补充只允许已有服务端核验的澄清选择、保留/说明回复及PendingScopeEditAgent明确编辑。无法核验的补充恢复原待补问题并继续询问，不将补充文字变成无条件独立查询。明确完整新问题应另行发送。

内联恢复使用内部限定历史进入正常Omni链路，只保存一条实际请求；会话串行锁仍覆盖全轮。完成查询生成新的执行记录和比较快照，不复制原待补记录的权限。实际用户请求、执行完整问题、原编号及补充部分分别记录。

## 前端和快照语义

普通SQL待澄清回答增加“恢复这轮待补条件”按钮，与成功查询的“引用这次查询”分开。按钮绑定原会话，发送前恢复上下文模式；其他会话或忙碌状态不能触发该按钮。

编号对应具体历史轮次，恢复旧编号会回到那一轮的条件，不自动升级到之后修改过的条件。页面明确说明该语义，恢复回答注明尚未执行。旧选项仍失效，重新生成的选项可以继续补全。执行阶段名称显示“恢复待补问题”和“修改查询条件”。
