# NL2SQL 通用字段理解与上下文升级

日期：2026-10-09。实现目录：`D:/ICT8-OmniAgent`。

## 目标与处理方法

用户提出的“本金”是口语表达示例。系统依据当前数据库和业务定义识别字段，不把金融本金固定替换成销售成本，也不按演示库的表名选择字段。

处理链为：用户原话 → 当前 Schema/业务别名/指标定义组成的本地概念图 → 可信历史范围 → 独立规划与核验 → 只读 SQL → 原表及单元格来源。已有模型规划仍可处理本地解析不能覆盖的问题；本轮概念归一化不新增模型请求。

| 用户表达或情况 | 绑定依据与行为 |
|---|---|
| 营业额、卖了多少钱 | 绑定实际收入字段，区分目标收入、归因收入和每件收入 |
| 卖出去多少件、进货几件 | 区分销售数量、采购数量和库存数量 |
| 回款到账、运货花的钱、工资发了多少 | 分别匹配回款、运费、工资总额；基本工资独立保留 |
| 本金、本钱 | 金融语境使用真实本金字段；商品语境使用有依据的成本；多个合理口径先澄清 |
| 净利润、毛利、税前利润 | 保留不同口径，缺净利润字段不会改查毛利 |
| 那华南呢、同样条件换成订单数 | 继承已成功查询的时间、地区和其余条件，重新查询数据 |
| 派生指标追问 | 同时核验物理依赖、输出、公式和 Catalog 版本 |
| 成本是什么、网页浏览量的指标定义 | 进入知识库定义检索，不执行无范围数值汇总 |

实际字段名、显式业务别名、引号字符串和真实数据库取值受到保护。未知概念或同权候选会要求确认，避免错误答案看起来很确定。对于完全匿名且没有业务说明的字段，例如只有 `x17`，系统不能凭字段名猜出真实业务含义；需要提供别名或指标定义。

## 实现位置

- `ict-track8/backend/nl2sql/semantic_graph.py`：业务概念、真实指标、物理字段和派生定义的连接；字面量保护、歧义与口径检查。
- `nl2sql/engine.py`、`schema.py`、`planner.py`：统一归一化入口、Schema 与别名缓存、日期字段绑定、独立意图核验。
- `conversational_sql_edit.py`、`executed_scope_edit.py`、`sql_history_scope.py`：多轮原子编辑、成功执行凭证与原筛选条件保留。
- `semantic_pending.py`、`session.py`、`omni_agent.py`：字段澄清侧记录、唯一选项、原始问题重解析和统一入口。
- `unified_routing.py`：字段定义与统计问题的路由边界。
- `nl2sql/value_index.py`：只对问题中出现的值执行后续匹配，减少旧查询路径的重复正则开销。

字段澄清记录不作为成功 SQL 来源。确认字段时必须保留原问题的其他条件，并检查当前数据库、Schema、业务别名、指标定义和会话依据；版本变化或记录不完整时拒绝执行。

概念图、Schema 别名和归一化结果使用有界缓存。新增本地语法不调用 API，旧规范问题走快速入口；实际性能与正确率以冻结评测和部署后的 HTTP 结果为准。
