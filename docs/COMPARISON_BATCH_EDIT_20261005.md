# 双侧修改、连续澄清和暂存发布

新增 `ConversationComparisonBatchEditAgent`，通过已有单侧修改Agent与比较Agent执行，不重写SQL验证器。其职责是明确两侧角色、暂存已完成查询、恢复当前澄清、核对来源与最后同时更新结果。

## 能力

- “把基准查询改成2024年；把比较查询改成2024年”，逗号分隔的两个明确角色也可使用。
- “两边都换成2024年”或“两项查询同时改成2024年”，同一明确条件作用于两侧，各自保留原查询其他条件。
- 两侧同时换指标，可经过第一侧与旧第二侧暂时指标不一致的阶段，完成第二侧后再统一校验。
- 以原比较方向解释基准/比较角色，反向基准时不误用时间先后序号；重复指向同一来源在执行前拒绝。
- 两侧可以分别经历缺时间→年份→粒度澄清，第一侧完成后仍不发布部分结果；SQLite会话重建继续第二侧。统一clarify接口的服务端选项确认也回到该子流程。
- 跨年月份查询都完成但无法按完整年月对应时，两项结果继续暂存，用户选择按月份对齐或先换基准再对齐，无需重新执行SQL。
- 第二侧失败、取消、来源版本变化或状态摘要不一致时，原来源保持不变。取消暂存不表示回滚SQL写入，所有查询原本就是只读。

保存的是原context一次及已改变来源的暂存快照，不每次复制两个完整context；暂存context/batch/pending编码总量超过28000字符时明确拒绝，预留会话大小空间。`comparison_pending_batch`不进入API公开状态或意图模型history，只有完成数/当前补哪侧等进度可展示。摘要为一致性检查，不是防管理员的签名。

前端区分“已暂存”和“已更新”，成功后展示两侧旧问题→新问题；取消入口不重复，阶段名称使用正式中文。
